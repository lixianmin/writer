- Consistent read view
  - 一致性视图，一致性是约束，ACID中的C
  - RC与RR的区别在于一致性视图的创建时机以及使用方式上
- Select
  - 简单的select语句不拿锁：只是把
read view中的数据拿出来展示罢了
    - 不会阻碍其它事务write数据
    - 不会被其它持锁事务阻碍read数据
    - 所以QPS > TPS
  - 简单select出来的数据，都是用于展示的，
看看可以，别当真，它们一定不是最新的
- Read Commited
  - 不可重复读
    - 在RC中，每条select语句都会创建一个单独的一致性视图，因此每次得到的数据都是最新提交的
  - 优势
    - RC不存在间隙锁（gap lock），因此发生死锁的机率比RR要小得多
    - RC中如果where中的查询条件未命中“索引”只会锁行，而在RR中相同情况下会锁表
    - 在RC隔离级别下，半一致性读(semi-consistent)特性增加了update操作的并发性
  - 问题
    - 不可重复读：即然数据只能用于show而无法用于update，那么读到最新的数据应该更开心啊
    - 主从复制：MySQL默认使用RR的理由是曾经它的binlog只能支持statement级别，而现在binlog已经支持row级别，此时RC下主从复制也不会有bug了
- Repeatable Read
  - 可重复读
    - 在RR中，默认第一次select时创建一致性视图，之后所有的select语句都使用同一个一性性视图
      - insert语句不会创建一致性视图
      - 然而这种做法对update提供不了任何帮助，update需要走current read
    - 如果想在启动事务时创建一致性视图，可以使用start transaction with consistent snapshot;
  - gap lock
  - 索引未命中锁全表
  - Phantom read
    - 幻读
- CurrentRead
  - S锁
    - select ... lock in share mode
    - 共享锁，就像美女，就是给你看看，别摸。想摸？可以啊，娶她，拿X锁 (= =)
  - X锁
    - 悲观锁（写高）：select ... for update
    - 乐观锁（读高）：update... where version=old
    - X锁是互斥的，在持锁事务未commit
之前，其它事务会一直卡死
