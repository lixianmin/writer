- 运营
  - 发公告前一定要跟产品和研发确认，研发可能由于原因延期，一旦公告发了，大家都很被动
- 产品
  - 协调好进度，一旦研发卡进度，及时调整进度
  - 临近上线不能加（改）需求
- 研发
  - 上线邮件
    - 通知相关人员，讲清楚潜在影响，请求及时反馈
  - Code Review
    - 直属领导审查，新项目至少要审三遍
    - 领域专家审查
  - 程序负责人
    - 统筹整体研发进度，及时反馈进度给产品
    - 撰写部署文档
    - 服务器占用的端口写到端口分配文档中
    - 服务器使用的ErrorCode写到ErrorCode分配文档中
    - 在gitlab中增加ci的web钩子
    - Staging环境是否需要多台服务器？
  - 代码合并
    - 提测到test前务必修改docker-compose中的image版本号
    - 从gitlab创建合并请求
    - 合并完成后git diff比较代码一致性
    - 查看ci状态，防止发布失败
  - 部署文档
    - 部署时间
    - 涉及域名
    - 提前两天给运维部署文档，运维需要时间准备
    - 上午开始部署：运维从发布到调试权限通过至少需要6个小时
    - 待部署项目列表，含受影响的老项目
    - 安排项目间上线顺序，修改文档中的部署进度
    - 配置清单
      - ECS：几台？CPU, 内存
      - MySQL：CPU, 内存，硬盘，主从还是只读
      - Redis：内存，读高还是写高，是否主从
      - 网段：16？32？
      - 端口：并记得写到端口分配文档中
    - 网络打通
      - 每台服务器需要跟其它的哪些服务器交互
      - 调用方向：服务器之间的谁调用谁
    - Apollo配置清单
      - 所有需要连接的服务器的地址，密码
    - MySQL
      - 新建数据库名
      - 在哪个数据库中？创建表/修改表的语句？
  - 上线后
    - 查看错误日志
      - mysql
      - redis
      - timescaledb
    - 钉钉：启动成功提醒
    - 钉钉：error报警
- 测试
  - 上线前：系统测试
  - 上线后：回归测试
- 运维
  - 白天、晚上都需要有权限的人在
