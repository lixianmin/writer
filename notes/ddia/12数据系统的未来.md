- 1. Data Integration
  - 1. 单一方案很难兼具鲁棒与性能，什么都想要的结局一定很糟糕
2. 厂商不会告诉你它们的软件不适应哪些场景
  - Combinging Specialized Tools by Deriving Data
    - 1. 对某些人无用的特性对他人则可能是核心需求
2. 数据集成通常在缩小并考虑整个组织框架内的数据流时才会变得更加凸显。
    - 1. 不同的访问模式需要不同的存储系统
2. CDC：写DB是向系统提供新输入的唯一途径
3. 双写：写交叉（顺序不同），部分失败（原子提交）
    - 1. 分布式事务：2PC，同步、实时；倾向于扩散错误；单点问题+性能差；线性一致性，读自己写
2. 事件日志：CDC，异步、延迟；倾向于把错误局部化；可确定性；重试+幂等，最终一致性
    - 1. 全序要求单一主节点，分区提高性能，但会导致乱序
2. 数据中心拥有各自的主节点，因此顺序不确定
3. 微服务之间无共享状态，因此顺序不确定
4. 如果client持有状态，则可能跟server的事件顺序不同
5. 多数consensus算法都假定单一主节点
  - Batch and Stream Processing
    - 1. 批处理 & 流处理 => 均输出衍生数据
2. 批处理是有界数据 vs. 流处理是无界数据
    - 1. 批处理的函数式倾向：鼓励确定性+纯函数，输入决定输出，容错性好，简化数据流分析
2. 同步：更新数据的时候也更新索引，出错时倾向于回滚整个事务，把错误范围扩大化
3. 异步：出错时倾向于把错误局部化，更加鲁棒
    - 1. 支持新功能，应对需求改变
2. 缺少重新处理数据的能力，会限制schema的演化，只能简单的加字段或记录
3. 反之，则会使得构建全新的数据模型成为可能
4. 渐进式演化：新老数据视图并存，利于测试和修复新视图bug，可随时回滚到老视图
    - 1. 并行运行两个系统：流处理提供实时性，批处理保证正确性
2. 调试、维护困难
3. 合并数据困难
4. 批处理的缺点：每次处理全量数据有可能代价高昂，而处理增量数据则会增加逻辑复杂性
    - 1. 同一个引擎可以处理：最新+历史数据
2. EOS：支持exactly once semantics
3. 支持event time而非process time窗口化，重新处理历史数据时process time毫无意义
- 2. Unbundling Databases
分离式数据库
  - 1. 都存储数据，核心都是信息管理系统
2. OS：低级抽象，底层硬件；字节序列
3. DB：高级抽象，隐藏存储复杂性、并发、crash恢复；SQL和事务
  - Composing Data Storage Technologies
    - 1. 新建索引、新建副本、新建CDC，三个过程很像：扫描快照+增量更新
2. 批处理、流处理、ETL：转换数据的存在形式，与DB中的保持索引和物化视图最新很像
    - 1. 为各种存储引擎和处理方法提供统一的查询接口
2. PG的外部数据包功能
3. 对外统一查询接口，但内部实现非常复杂
    - 1. 不存在适合所有访问模式的统一数据模型或存储格式
2. 把衍生数据系统看作不同类型的index，通过CDC和event log维护index，应用代码看作派生函数
3. 数据同步：系统内用trx，系统间用event log
4. 遵循unix传统：单一任务做好一件事，内部通过低级API（管道）通信，外部通过高级语言（shell）组合
5. pipe <=> event log, shell <=> 分离式DB；mysql | elasticsearch，类似于unix管道
  - Designing Applications Around Dataflow
    - 1. Excel每当输入更改时，会自动刷新公式，这与DB中自动更新index或缓存的视图类似
    - 1. DB专注存储，k8s等专注运维，应用无状态化
2. 代码中无法订阅变量值修改事件，只能轮询，或手动编写observer模式
3. DB内容变化时通常不会主动通知，只能轮询，CDC只是最近才出现的新功能
    - 1. 微服务方案：同步调用汇算服务
2. 数据流方案：通过轮询或订单，把汇率缓存到本地，更快更鲁棒
3. 购买事件 join 汇算事件：依赖时间
  - Observing Derived State
    - 1. 数据收集--> 存储 --> 查询，写路径+读路径
2. 各种优化最终都是为『查询』铺路
3. 写路径的优化叫index，包括衍生数据系统，索引会全量更新
4. 读路径的优化叫缓存，缓存只存储热点查询
5. 权衡写/读路径边界：多写会减少读负担；微博的push/pull模型
    - 1. 无状态client与请求/响应模式的思想根深蒂固
2. 低延迟：请求/响应 => pub/sub（IM, game）
- 3. Aiming for Correctness
正确性
  - 1. 正确使用基础设施的功能 (isolation, quorum配置)，如果配置难以理解，就很容易出错
  - The End-to-End Argument for Databases
    - 1. 不确定性（灾）：bug、人为失误、NPC
2. 容忍不确定性，更容易从bug中恢复
3. 不可变性+幂等
    - 1. TCP：基于session的序号
2. kafka：基于partition的offset
3. fencing：处理节点失效、leader切换
4. e2e的正确性：需要解决人为重试导致的重复；sender带uuid，receiver先insert去重表
    - 1. 基础设施：TCP去重、以太网校验、WIFI加密、事务（并发写、约束、崩溃、网络中断、磁盘损坏）
2. 基础设施可以减少上层出问题的可能性，但仅依赖底层基础设施是不够的
  - Enforcing Constraints
  - Timelines and Integrity
    - 1. transaction时效性很强，而event log时效性很差
2. CAP中的C是时效性，可以违反；ACID中的C是完整性，不能违反
    - 1. 真实系统中，道歉和补偿很可能是常规业务流程，因此弱化版的一致性往往是可以接受的
2. 契合点：小范围内使用trx保证时效性，大范围内使用event log保证完整性
  - Trust, but Verify
    - 1. 打卡，但不考勤
2. e2e：单靠基础设施不可能避免所有错误
    - 1. 硬件：磁盘上的数据也可能默默地坏掉
2. 软件：广泛验证软件也会有bug，MySQL可能破坏unique约束，PG的SSI可能write skew
    - 1. 基于事件的系统有更好的可审计性
2. e2e的审计可含盖磁盘、网络、服务、算法等中间路径
3. 自动化测试&审计：增加发现bug的可能性，为软件快速迭代提供信心
- 4. Doing the Right Thing
  - Predictive Analytics
    - 1. 信用评分总结了『你以前的行为』，而预测分析则通常基于『谁与你类似』，那么那些被放错了位置的人呢？
2. 基于统计的数据，落实到个人就是概率性的
  - Privacy and Tracking
    - 1. 服务用户个人：保存用户明确输入的数据
2. 服务公司利益或广告商：跟踪记录用户的活动
    - 1. 在我们监控驱动的组织，我们收集实时监控流，并将其存储在监控仓库，监测科学家分析和监测处理，以获得新的见解
2. 迄今为止世界上最大规模的监控基础设施，不同之处在于数据由很多公司而不是政府收集
