- Linearizability
  - 可线性化
    - 1.external一致性: 多副本对外看起来就像是单一副本，原子性，无并发
2. 全序关系：任意两个操作都可以比较先后顺序
3. 性能差
    - 可线性化应用：
1. 约束与唯一性保证：所有节点对最新值达成一致，唯一名、文件路径、账户余额、库存情况
2. 跨通道的时间依赖：Alice高呼比分
  - 对比
    - Serializability
      - 1. 事务隔离属性
2.事务顺序与串行顺序可以不同，但结果得相同
3. 三种可串行化实现中：2PL与actual serial execution是线性化的；SSI是非线性化的
    - Linearizability
      - 1. 最新值保证，原子性
2. 无法避免write skew等问题
    - 1. 事务一致性：多对象、多操作、单副本
2. 数据一致性：单对象、单操作、多副本
3. 参考《强一致性：别再用BASE做借口，来看看什么是真正的事务一致性》 ([链接](https://time.geekbang.org/column/article/272999))
  - 实现
    - 主从复制
      - 1. 部分可线性化
2. 同步复制：写主节点；线性化读主节点或同步节点；小心社会性死亡的主节点对外提供服务
3. 异步复制：切主时可能违反持久性和线性化
    - 共识算法
      - 1. 可线性化
2. 内置措施：防脑裂，防过期副本
    - 多主复制
      - 1. 不可线性化
2. 异步复制：多节点并发写，需处理写冲突
3. 断网时写操作暂存在本地，适合多数据中心
    - 无主复制
      - 1. 很难线性化
2. w+r>n无法确保线性化: (Cassandra) 墙上时钟和LWW，无法保证时间戳与事件顺序一致
3. 读修复：r+w可线性化，但cas需共识算法
  - CAP
    - 1. CP：保线性化，弃可用性
2. AP：多主复制，弃线性化，各副本独立处理写请求，更能容忍网络故障
  - 可线性化与网络延迟
    - 1. 多核CPU内存是非线性化的（除非内存屏障或fence指令）
2. 计算机内部通信是可靠的，异步刷新对CPU性能至关重要，放弃线性化是因为性能而不是容错
- 顺序保证
  - 因果一致性
    - 1. 部分有序，允许并发操作，无法区分先后顺序
2. 参考git的分支合并图
3. 可豁免网络延迟影响的最强一致性模型
4. 读倾斜违反因果一致，读到了本不应看到的数据
    - 对比：
1. 可线性化：全序关系，无并发操作，性能差
2. 因果关系：偏序，并发的事件无法排序
  - 序列号排序
    - 因果序列发生器
      - 1. 逻辑时钟，递增计数器，全序关系
2. 主从复制：主节点定义因果顺序
    - 非因果序列发生器
      - 1. 各节点独立生成奇偶数序列号
2. 基于物理时钟的精度足够高的时间戳
3. 区间分配器：为各节点预分配序列号段
      - 1. 比唯一主节点可扩展性更好
2. 每个操作具有唯一的、近似增加的序列号
3. 序列号与因果关系并不严格一致
      - 1. 偶数计数器生产速度可能远落后于奇数计数器
2. 时钟偏移会影响物理时钟
3. 区间分配器无法判断因果序
    - Lamport时间戳
      - 1. 与因果序一致的全序关系（total ordering）
2. 按(counter, node ID)全局排序
3. 每次请求和响应都携带当前最大counter
      - 对比：
1. 版本向量：区分两个操作是并发还是因果依赖
2. Lamport时间戳：确保全序关系
      - 1. 仅时间戳排序无法解决唯一性约束问题
2. 需要知道其它节点的执行情况
  - 全序关系广播
    - 安全属性
      - 1. 可靠投递：消息无冗余或丢失（exactly once）
2.有序投递：顺序在发送时决定，并依序到达各节点
      - 1. 重试：从节点或网络故障中恢复
    - 使用全序关系广播
      - 1. 状态机复制、可串行化事务、fencing令牌锁
2. 可以将全序广播视为日志：复制日志、WAL
3. 全序广播基于异步模型，不保证何时发送成功
    - zk与etcd
      - 1. etcd和zk默认线性化写，顺序一致性
2. etcd法定票数读：把读请求排序并广播，所有节点读取追加的日志，本节点收到消息后再读取
3. zk读前sync()：查找到最新消息的位置，等接收到该位置之前的所有消息后再读取
4. 从同步更新的副本上读取：可用于链式复制
      - 1. 数据量小，内存完全放得下
2. 数据变化频率低（分钟/小时）
3. 节点之间使用全序广播同步数据
- 分布式事务与共识
  - 2PC
    - 流程
      - 1. app从协调者处获取全局unique的txid
3. 参与者基于txid完成本地事务
4. prepare：参与者的回答是promise，无法反悔
5. commit point：协调者将决定先落盘后通知，不断重试通知直到成功（阻塞性原子提交协议）
    - coordinator
      - 1. application进程可以作为协调者
2. 不再是stateless服务，无法随意增删
3. 协调者本质是DB，小心单点问题
    - 未决状态
      - 1. 参与者回复yes，但未收到协调者指令
2. DB的数据被lock，这会阻止其它事务修改甚至读取数据，即使DB重启也不解决问题
3. 如果协调者有bug，则被锁定的数据无法自动恢复
4. 手动恢复非常消耗体力（小心大促）
    - 1.. 运维故障、性能差（fsync, network round-trip）导致云厂商不愿提供2PC
2. MySQL的分布式事务比单机事务性能差10倍
3. 只支持2PL，不支持SSI
4. 倾向于放大失败，与构建容错系统的目标冲突
  - 共识算法的可容错性
    - 共识算法
      - 1. 协商一致性：所有节点对决策达成一致共识
2. 诚实性：一旦决策，不可撤销（RC基石）
3. 合法性：决议的值v一定是某个节点提议的
4. 可终止性：活性属性，只要超半数节点存活，则终将达成共识，消息不会丢失
    - epoch与quorums
      - 1. epoch：单调递增，任期大者为有效leader
2. leader提议，quorums决策
3. 在选主和决策两轮投票中，必然有重叠的节点
4. 与2PC的区别：是否所有节点投票；单点问题
      - 1. 选主：无法保证同时只有一个leader，但业务方可以通过任期确定谁是当前leader
2.成员服务：无法准确探测有效节点集合，但可以让集群对一个可用的有效节点集合达成共识
3. zk和etcd不好使，但仍然比重复造轮子简单
    - 共识算法的限制
      - 1. 投票是同步的，速度慢
2. 网络故障时，majority可正常运行，少数派会卡死
3. 投票的node集合通常是固定的，无法动态调整
4. 基于超时判定节点失败，存在误伤，导致频繁切主
5. 对网络问题敏感
- Summary
  - 等价问题类
    - 1. 可线性化CAS寄存器：单调自增id, 发号器
2. 原子事务提交：DB是否提交/中止分布式事务
3. 全序广播：可靠、有序的投递消息
4. 分布式锁：多个客户端抢lock或lease
5. 成员服务：就集群内的有效节点达成共识
6. 唯一性约束：多事务使用相同的key创建记录
  - 知识提要
    - 1. lamport时间戳：因果序
2. 2PC：原子提交（也算共识算法），决策
3. epoch：任期，选主，防脑裂
4. quorums：多数派，决策，容错
5. 线性一致性：不一致但外面观察不到，raft
6. 最终一致性：不一致还被观察到了，gossip
7. 全序广播："全"不丢(重试)不重(幂等); "序" 有序
8. 主节点：日志定序
  - 处理主节点崩溃
    - 1. 坐等恢复：接受系统阻塞 (不满足可终止性)
2. 手动选主：实践中通常OK (不满足可终止性)
3. 自动选主：面临脑裂问题
- Consistency保证
  - 最终一致性
    - 1. 也许称为『收敛』更贴切
2. 弱：收敛之前无法保证读成功或返回什么值
2. 时刻谨记：系统平时正常，高并发时掉链子
  - 更强的一致性
    - 1. 性能更差，但容易正确地使用
2. 分布式一致性：delay和faults，协调副本状态
3. 事务隔离级别：并发事务，避免竞态条件
