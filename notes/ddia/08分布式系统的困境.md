- NPC
  - Network Delay
    - 两军问题
      - 1. 请求丢失
2. 远程节点宕机
3. 响应丢失
      - 1. 异步网络无法区分这三种情况
2. TCP三次握手，auto-ack与resend
    - 应对措施
      - 1. 超时：无奈之举；报错或重试？
2. 重试：幂等；重试策略、重试限流
  - Process Pause
    - 1. GC：分钟级STW（HBase）
2. 虚拟机：Swap分区导致进程挂起
3. 同步磁盘IO：防不胜防（class loader）
  - Clock Drift
    - 墙上时钟
      - 1. NTP同步会导致墙上时钟跳跃和回溯
2. 适合：当前时间
3. 墙上时钟会忽略闰秒（一分钟含：59s/61s）
4. 受温度影响，漂移量：6ms / 每30秒同步
5. 受Network Delay影响
6. 管理员可能故意设置错误的时间
    - 单调时钟
      - 1. NTP会影响单调时钟的步进频率，但不会回溯
2. 适合：计算时间差
3. 单调时钟基于机器启动时间，绝对值没有意义
4. 将不同机器的单调时钟进行比较也没有意义
    - 其它
      - 1. 时钟漂移太厉害的节点应该被投票死亡
2. 使用逻辑时钟代替物理时钟
3. 读时钟时返回置信区间
- Others
  - 1. 必须容忍部分失败并构建容错机制
- 知识真相与谎言
  - 安全性与活性
    - 1. 安全性：系统可以失败但不能返回错误结果，安全性必须一直持有，即使系统崩溃和网络失败
2. 示例：唯一性，单调顺序
    - 1. 活性：可以暂时不满足，但在系统恢复正常后必须收敛于满足状态
2. 示例：可用性
- 系统模型
  - Network Model
    - Reliable (perfect) links
      - 可乱序，但不重不丢
    - Fair-loss links
      - 可重、可丢、可乱序
    - Arbitrary links
      - 恶意监听、篡改
  - Failure Model
    - Crash-stop
      - 随时崩溃，永远消失
    - Omissions
      - 1. 不接收请求或不返回响应
2. 通过heatbeat或ping/pong探测
    - Crash-recovery
      - 1. 随时崩溃，但可以恢复
2. 未持久化的内存状态可能丢失
3. 通过docker或supervisor重启
    - Byzantine
      - 进程可以做任何事情，包括作弊和欺骗
  - Timing Model
    - 同步模型
      - 1. 假定NPC仨问题都是有清楚的上界的
2. 多数系统并非同步模型，无限延迟确实存在
    - 异步模型
      - 算法不对时机做任何假设，甚至没有时钟或超时
    - 部分同步模型
      - 1. 多数时间系统像同步系统一样运行
2. 偶尔会超时NPC问题的预期上界
3. 比较实际的模型，系统设计需要考虑极端情况

### 关系

- 可重、可丢、可乱序 → 可乱序，但不重不丢 (retry+dedup)
- 恶意监听、篡改 → 可重、可丢、可乱序 (TLS)
