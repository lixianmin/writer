# 事务

- 六大异象
  - 脏读
    - 1. 事务看到部分更新，或稍后被回滚的数据
    - 方案：MVCC
  - 脏写
    - 1. Uncommitted数据被其它事务覆盖
2. 所有的隔离级别都需要防止脏写
    - 方案：写锁（RC, SI）
  - 读倾斜/不
可重复读
    - 1. 先后读不同快照的部分数据，结果集不一致
2. 快照之前的数据应可见, 之后的事件应不可见, 读倾斜违反因果关系, 读到了本不可见的数据
3. 场景：只读长事务，如数据备份、分析、校验
    - 方案：SI满足因果一致性，只要查询到某些数据，则一定可以看到触发该数据的前序事件
  - 写倾斜
    - 1. 两笔事务并行更新两个不同的对象
2. 示例：医生换班
  - Lost Update
    - 1. 两个事务并行read-modify-write同一对象
2. 最常见的异象：ORM框架容易导致更新丢失；ConcurrentHashMap是否线程安全的问题；递增计数、余额更新、wiki编辑
    - 1. 原子写：使用系统原子指令，理论上最快
2.乐观锁(CAS, RVW): 设计模式, 基于版本; ABA问题
3. 悲观锁(2PL, VRW): select ... for update
4. 更新丢失检测：主流DB中只有InnoDB不支持
  - 幻读
    - 1. 本想见缝插针，奈何慢人一步
2. 因为预期结果为空，所以缺少实体用于加锁
3. 示例：抢车位
- 隔离级别
  - Serializable
    - 单线程串行
      - 1. 2007年，无锁开销，吞吐量受限于单核CPU
2. 存储过程封装事务：redis(lua), VoltDB(java)
3. 事务必须简短且高效，否则影响其它事务
4. 活动数据集必须完全在内存中，否则严重拖慢
3. 跨分区事务占比必须很小：VoltDB
    - 2PL
      - 1. 因为2PL是串行化方案，因此可防止所有异象
2. 显式锁就是2PL，2PL就是RWMutex
3. InnoDB的串行化，select会加行锁或间隙锁
4. 2PL严重影响并发度，访问延迟很难确定，吞吐量和响应时间相比其它弱隔离级别下降很多
5. 如果没有合适的索引加锁，就锁表，性能骤降
    - SSI
      - 1. 乐观并发控制，事务提交时如果冲突则回滚
2. 基于SI，只读查询不需要加锁
  - 命名混淆
    - 1. Oracle的将SI称为可串行化
2. PG和MySQL将SI称为可重复读
3. 不同DB实现的RR提供的保证大相径庭
4. DB2的RR实际上是Serializable
- ACID：A容错C酱油I并发D吹牛
  - Abortablity
    - 1. 目标: 多对象统一步伐, 简化应用层错误处理
2.方案: redo(retry, kafka多消费者代替2PC), undo(rollback, 数据库undo log)
3. multistage pipeline: plain select查账判断可否转账，解决OLTP事务余额不足回滚的问题
3. 无主复制的DB会部分失败 ([链接](https://queue.acm.org/detail.cfm?id=3321612))
  - Consistency
    - 1. 应用层逻辑决定数据是否合法，DB打酱油
2. 也许应该称为AID
  - Isolation
    - 1. 目标：研究并发导致的各类读写异象
2.方案：读快照+写锁; kafka:分区内有序, 分区间并发
3. 读写分离：无锁方案提升读速度，除快照外，搜索引擎常用：双buffer、增量索引
  - Durability
    - 1. 落盘：WAL日志（redo log）
2.副本：日志复制 (binlog, 共享存储, 共识算法)
3. binlog影分身；redo log满血复活；undo log 时间回溯
    - 1. 不存在完美的持久性
2. SSD突然断电：fsync的数据也有可能无法恢复；接下来的几周可能丢失数据，与温度相关
3. HDD比SSD：坏道率更低，但整盘损坏率高
- 读：多表一致
写：重试安全
  - 1. 多对象（表、索引）读/写一致
2. 不担心部分失败，看不到中间结果
3. 宕机、崩溃、断网、磁盘满、竞态数据
  - BASE：唯一承诺的就是它不是ACID
  - 1. 事务成功&网络断开 => 应用层去重
2. 重试overload错误会进一步压跨DB
3. 重试有副效应（发短信）的事务需要去重
  - 1. 单机：原子性（undo），持久性（落盘）
2. 集群：原子性（redo），持久性（副本）
