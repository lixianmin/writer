# 流处理

> 📎 原始文件: [11流处理.xmind](file:///Users/xmli/me/writer/notes/ddia/11%E6%B5%81%E5%A4%84%E7%90%86.xmind)

- Transmitting Event Streams
  - 批处理
    - 1. 基于文件, 可反复重试, 方便试验、故障恢复
2. 可被多个job读取，按文件名归类
3. 使用poll方式消费，间隔周期长，代价低
4. 高可用：失败自动重试，不完整输出自动丢弃
  - 流处理
    - 1. 基于事件, 按topic组织, 带wall-clock时间戳
2. 可被多个消费者订阅，按topic归类
3. 主动通知消费者（频繁poll代价太高）
4. 传统DB不支持推送，trigger开销大且不稳定
- Database and Streams
  - Keeping Systems in Sync
    - 1. OLTP用户查询, Cache读, Index搜索, DW分析
2. dual writes: 写交叉(并发), 部分失败(容错)
3. 复制状态机: 单主系统
  - Change Data Capture
    - 1. 衍生数据系统: log的消费者
2. 通常异步: 方便运维但有lag问题
3. 初始快照: rdb
4. log compact: aof, kafka, 替换重复的key
5. kafka connect: 啥DB都支持
  - Event Sourcing
    - 1. CDC：应用操作DB，对衍生数据系统无感知；每条日志包含全的record状态，可以压缩
2. 事件溯源：应用以记录event为目的；日志中是用户action，无法压缩
3. Event: 用户动作, 已成fact, 不可取消, 不可修改
4. Command: 用户指令, 可能失败（比如验证）；失败不能以异步方式完成
  - State, Streams, and Immutability
    - 1. DB存储当前状态，利于查询
2. changelog：历史比结果能反映出更多的信息
3. 同时运行2套系统，比改造旧系统schema容易
4. CQRS: schema设计复杂源于支持各类读模式
  - Concurrency control
    - 1. 主要缺点：异步消费（包括事件溯源和CDC）
2. 读自己写：写后读一致性
3. 事件溯源：绕过事务同时修改多对象的问题
- Processing Streams
  - Uses of Stream Processing
    - 1. CEP：复杂事件处理，基于事件的模式查询
2. 流分析：计算窗口聚合
3. 物化视图：保持派生数据系统处于最新状态
  - Reasoning About Time
    - Processing Time
      - 1. 对延迟处理、重新处理不友好
    - Event Time
      - 1. 无法确定时间窗内的事件在什么时间全部收到
2. 方案一：丢弃迷失的消息，并监控
3. 方案二：不断修订
    - 1. 接收时间不靠谱，因为server可能宕机
2. 发送时间不靠谱，因为client时间随便调
3. 校正时间S=事件时间C+接收时间S-发送时间C
    - 窗口类型
      - 1. Tumbling (翻滚窗口): 长度固定, 边界明确, 窗口紧邻&互不重叠
2. Hopping (跳跃窗口): 长度固定, 边界明确, 部分重叠以平滑过渡
3. Sliding (滑动窗口): 长度固定, 边界无法预测, 基于事件滑动前进
4. Session (会话窗口): 长度不固定, 按用户分组, 用于会话分析
  - Stream Joins
    - 流和流join
      - 1. 窗口join
    - 流和表join
      - 1. 流 (用户事件)，表(用户资料)
2. 使用DB数据丰富活动事件
3. 频繁查询DB很慢甚至会过载，将DB副本加载到流处理器中，通过CDC保持副本最新
    - 表和表join
      - 1. 物化视图维护
- 消息系统
  - 1. 可用于实现事件通知
2. unix pipe, tcp ，单sender&receiver
3. 消费过缓：丢弃, 缓冲(MQ), 背压(tcp)
4. 节点崩溃：持久化（磁盘、副本）、接受偶尔丢消息（更好的吞吐和低延迟）
  - 直接消息传递
    - 1. UDP组播：低延迟，股票行情
2. 无代理消息库：ZeroMQ, nanomsg
3. webhook：通过回调url接收事件
4. 需要假定双方一直在线，否则消息会丢失
  - MQ（Message Broker）
    - 1. 本质上是一种面向消息流的DB
2. 更容易容忍clients的频繁上下线
3. 代理（broker）负责durability
4. 配置决定：消息只写内存、写磁盘、写副本
5. 消费过缓：允许无限队列
6. 异步消费：消息积压可能导致明显的消费延迟
    - 消费模式
(多消费者)
      - 1. load balancing: 共享订阅, 提高性能
2. fan-out: 各自订阅, 互不影响
3. redelivery+load balancing -> 消息乱序
    - AMQP/JMS
      - 1. 接收消息具有破坏性，导致消息从MQ删除
2. 例：RabbitMQ, ActiveMQ
    - Partitioned Logs
      - 1.接收消息是只读的，不修改日志，唯一副作用是消费者offset前移，类似批处理可反复重试
2. (循环) 缓冲满才会丢弃旧数据
3. group内load balancing，group间fan-out
      - 1. partitioned: 强调物理分区, 突破单机吞吐上限
2. queue: 保序, 因果一致
3. consumer与queue数相同, 想提并发加queue
4. 单个message消费过缓，会阻塞整个queue
  - MQ vs.DB
    - 1. DB中的数据会一直保留，直到被明确要求删除
2. 多数MQ假定当前工作集很小，如果消费过缓导致消息swap到磁盘，可能降低吞吐
3. DB支持索引和各类查询，MQ只支持订阅主题
4. DB只能poll发现修改，MQ主动推送新消息
- 系统间同步
  - 1. 四类系统：DB在线业务；缓存加速查询；ES全文索引；数仓离线分析
2. 双写：请求交叉（顺序不一致），部分失败（原子提交，2PC）
3. 双删：cache aside
4. CDC：变更数据捕获, 解析复制日志, 复制滞后
5. 事件溯源：事件日志, 只追加, 不更新
6. 区别：CDC含新旧版本值，事件溯源只含用户意图

### 关系

- 1. load balancing: 共享订阅, 提高性能

2. (循环) 缓冲满才会丢弃旧数据
3. group内load balancing，group间fan-out
